Project kickoff — portfolio design decisions

Started my interactive portfolio project today. Decided on the core interactive features it needs to have: a mobile hamburger nav, a contact form with client-side validation (name, email, message — checking all fields are filled and the email format is valid before submit), and a project filter by category as the third interactive piece.

The filter needed more thought than I expected. Since all my current projects are frontend, and this is actually my first project using JavaScript at all, a generic "frontend/backend" split didn't make sense. Landed on filtering by things like tech used, project type, and skill demonstrated instead — more honest, and it lets the filter grow with me. Also decided I want it fully data-driven: each project card gets data-category attributes, and the JS reads whatever categories exist on the page and builds the filter buttons automatically. That means I can add new projects with new categories later and the filter just adapts — no touching the JS again. Projects can belong to more than one category, and there's always an "All" button by default.

For the visual direction, I described the vibe I wanted — serious, hard-working, "gets the job done," not flashy or bold, but showing willingness to learn and put in the work. Landed on a direction we're calling "the workshop" — near-black graphite background instead of pure black, one confident burnt-orange accent used sparingly, monospace labels for a technical/blueprint feel, Space Grotesk for headings and Inter for body text. Locked in the full color palette as CSS variables, the type pairing with fallback fonts, a type scale, and an 8px base spacing unit.

Also worked through when to group shared CSS properties (like font-family and font-weight across all headings) versus keeping properties separate when they vary (like font-size and line-height per heading level) — group what's shared, separate what's different.

Moved into writing actual content today instead of touching HTML, since it made more sense to know what I'm saying before deciding how to structure it. This turned out to be the hardest part so far — I'm confident in the work itself, but writing about myself doesn't come naturally.

For the Hero, I worked through my actual background (self-taught, one skill at a time, pausing to make sure I really understand something before moving on) and landed on: "Self-taught, one skill at a time. I don't move on until I've actually got it." Kept the title plain — "Frontend Developer," no qualifiers like "junior" or "in training," since the honesty of the rest of the content already does that work.

For About, I was honest about how I actually got into frontend — it started as the fastest path into freelancing, but I got hooked on watching something grow from nothing into a finished thing in front of me. Wrote about my self-taught process, the logging habit (which is literally what I'm doing right now), and closed with "I'm not done learning. I don't plan to be."

For Skills, I decided to split things into "what I know well" (HTML, CSS, Git) and "what I'm learning now" (JavaScript, advanced CSS/animation), with a one-line honest note under each — no inflating, no padding the list with things I don't actually know solidly. Left Python off the site entirely, since this is a frontend-focused page and I decided not to blur that positioning.

Also made a structural HTML decision: each distinct idea in a paragraph gets its own <p> tag rather than cramming multiple thoughts into one — better for both semantics/accessibility and for controlling spacing later.

Finished the Skills section content: split into "what I know well" (HTML, CSS, Git) and "what I'm learning now" (JavaScript, advanced CSS/animation), each with a one-line honest note. Left Python off entirely since this is a frontend-focused page.

Wrote a short two-sentence description and picked category tags: html-css-only, css-grid, and accessibility — pushed back on including "client-brief" as a tag since it describes the project's origin rather than something a recruiter would filter by, and was initially unsure about "accessibility" but kept it since running a Lighthouse audit and fixing a real contrast issue is a genuine, uncommon signal worth surfacing. More projects will populate the same slot later thanks to the data-driven filter system.

Also settled a semantic HTML question: project cards should be <article> elements, not <div> or <section>, since each card is self-contained content that would still make sense if pulled out of the page — that's the actual test for <article> vs <section>.

For Contact, wrote the intro line ("Have something in mind, or just want to say hi? Send me a message."), form field placeholders, submit button text, and direct links to LinkedIn, GitHub, and Frontend Mentor (left CodePen off, pending honest review of what's actually in it).

Worked through validation message structure with real care: error messages should live in JS logic (since they're conditional), but each field needs its own empty error <span> already in the HTML — one per field, positioned right under that specific input, not one shared message near the submit button. This handles multiple simultaneous errors properly and lets me use aria-describedby to connect each input to its own error text for screen readers.

Wrote the full HTML structure for all five sections, then went through a dedicated review pass with my design partner rather than jumping straight to CSS — caught a real handful of issues I wouldn't have noticed writing everything in one sitting.

Fixed a real anchor-link bug: the Skills section was using class="skills" instead of id="skills", so its nav link was silently doing nothing — fragment links only match ids, not classes. Same category of bug that showed up in the ceramics build log, good to catch it here too.

Added the hamburger menu button as a sibling of <nav> inside <header>, using three plain <span> elements rather than an SVG icon — decided that mid-review, since a hamburger benefits from animating into an X on open, and that's simpler with real HTML elements you can rotate via CSS than with SVG paths. Included aria-label and aria-expanded on the button so screen reader users get real state information, not just "button."

Fixed the project image: renamed the file to remove spaces and an & character (lowercase, hyphens — good general habit for any filename referenced in code), and replaced the empty alt="" with real descriptive alt text, since this image is actual content, not decoration.

Built out the full contact form: real labels, placeholders, and one empty error <span> per field (not one shared message), each connected to its input via aria-describedby — so JavaScript can fill in field-specific error text later, and screen readers announce the right message tied to the right field. Before diving into any single section, worked out the layout system that every section will share. Started with typography — locked in rem units for heading sizes instead of raw px, since rem scales with a user's browser font-size setting, which matters for accessibility. Switched the Google Fonts import from CSS @import to a <link> in the HTML head instead, since @import blocks the browser from fetching the font in parallel with the stylesheet — a real, if small, performance cost.

The bigger discussion was the content-width wrapper. Initially explored a two-variable system (--container-narrow / --container-wide with modifier classes), following the same narrow-for-prose, wide-for-grids logic from the ceramics project. But then realized only the Projects section actually needs to be wider — every other section is fine at the same default width. Pushed back on my own design partner's suggestion here and simplified it: one .container class with a sensible default max-width (720px), and a single targeted override — #projects .container { max-width: 1100px; } — for the one section that's actually different. Good lesson: don't build a flexible multi-variant system for a distinction that only has one real exception.

Also settled why a wrapper <div class="container"> inside each section is better than applying max-width directly to the <section> itself — it lets a section's background span full width later while keeping content centered and narrow, which the base section approach can't do.

Took a pause mid-session to reset — noticed we were jumping around without a clear order and stopped to regroup instead of pushing through. Decided explicitly: mobile-first, one section at a time, in document order, same discipline we used for HTML.

Confirmed body needed real color and line-height values that weren't there yet — settled a naming question in the process: --color-text is the sitewide default (used on body and inherited by headings), --color-text-muted is a selective override for genuinely secondary text, not a body-wide default. On desktop later, it'll spread nav links full-width with justify-content: space-between and a muted hairline underneath; that's queued for the desktop pass.

Built the mobile hamburger button: three styled <span> bars, transparent-into-background button with no default border. Decided on workflow order going forward: finish the full mobile version of every section first — Hero, About, Skills, Projects, Contact, form — before starting any desktop overrides. Reasoning: stay in one mental mode at a time, and get a complete, real, working mobile site as a milestone before layering in a second pass.

Styled About using flex-column + gap for paragraph spacing, same pattern as Hero — deliberately avoided margin for stacking prose, since margin collapsing between sibling block elements can produce unpredictable results, while gap on a flex container doesn't have that problem. Learned along the way that this collapsing behavior specifically doesn't apply to flex children either, which is why an element like h2 can safely have its own margin-bottom alongside a parent's gap — they add together predictably instead of merging, giving headings extra separation from body text without breaking the gap system.

Made a real architecture decision on section spacing: moved from padding-block on individual sections to a single padding-bottom on the shared .container class instead — since Hero's own vertical centering already provides enough separation from the top of the page, adding a full top-padding on About on top of that would've created too much dead space. This makes every section's spacing consistent and centralized in one place rather than repeated per-section. Flagged that Contact (the last section) will need this overridden later, since there's nothing after it to separate from.

Real bug caught after "finished" — form submission via Enter key

Found a genuine, easy-to-miss bug on my own, after the project was already marked complete: the submit handler was listening for a click on the submit button specifically, not a submit event on the form itself. That meant pressing Enter while focused in a text field — a completely normal, common way people submit forms — bypassed the click listener entirely, went straight to the browser's native form submission, and since action="" with no real backend, would reload the page and wipe out everything the user had typed, with validation never running at all.

Understood the fix before asking for confirmation, and specifically pushed back to make sure it was a minimal, safe change: swapped submitButton.addEventListener('click', ...) for form.addEventListener('submit', ...), changing nothing else inside the handler. Confirmed the reasoning myself — every validation function and the success logic only care that submission happened, not how it was triggered, so no other code needed to change. This single swap now correctly catches both the button click and the Enter-key path, since both ultimately fire the same underlying submit event.

Good final lesson from this project: "finished and tested" doesn't mean "tested against every real way a user might interact with it" — worth deliberately trying alternate interaction paths (keyboard, not just mouse) even after a feature feels done.
